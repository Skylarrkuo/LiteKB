# 阶段 4–5 验证口径

## 本地运行环境

控制台和 Worker 的最终验收使用 Windows x64、项目 Python 3.11 虚拟环境、本机 PostgreSQL 18.6（`127.0.0.1:5432/litekb`，`pgvector 0.8.7`）和 Redis 7.4。业务进程通过独立账号 `litekb_app` 连接。`/health/ready`、`/admin/` 和入口 JavaScript 均返回 HTTP 200。已实测管理员登录、读取个人资料及退出，Worker 已回应 `ping` 并注册 `litekb.execute_run`。pgvector 在独立的同版本 Windows PostgreSQL 实例中通过上游 14 项回归后安装。

下面的故障、质量与延迟数据来自另一个原生 PostgreSQL 16.15 / pgvector 0.8.6 实例。API 与单并发 Celery Worker 分进程运行，HTTP 仅监听回环地址。通过产品 API 创建知识库、上传合成文档、等待异步建索引并读取运行事件。跨模块回归中有 62 项通过，首次命令写错了融合模块路径，改用 `knowledge.vector.test_fusion` 后其中的 3 项也全部通过。SDK 从构建出的 wheel 安装后通过 5 项测试。控制台通过 Vue 类型检查和 Vite 生产构建。Docker 部署使用的 Linux 入口与 Gunicorn 留待服务器验收。

## Worker 与故障恢复

用一个可阻塞的本地向量 HTTP 接口接住正在执行的查询，然后终止正在处理这条 Run 的 Windows Celery 进程，启动替代 Worker。第二次复验在此期间只读 PostgreSQL，避免查询 API 触发补偿逻辑。替代 Worker 自动将该 Run 记为 `failed / worker_lost`。数据库中只有一次 `run.running`。从中断前的游标重连得到 `run.failed`，下一次独立提交正常返回文本。

写入故障另用了执行实际文件写入的子进程。进程在写出后退出，恢复后文件只有一条记录。已发出的外部调用若丢失响应，服务保留派发记录；调用方需要按业务 ID 核对外部结果。[运行状态和故障边界](run-api.md)

## 召回质量

评测集包括 48 段文本、32 个标注查询。向量来自在这套语料上训练的 12 维 LSA，检索实际执行 PostgreSQL 全文查询和 pgvector 距离排序。各指标取前三个命中，四种模式使用同一批语料和标注。

| 模式 | Recall@3 | MRR@3 | nDCG@3 |
| --- | ---: | ---: | ---: |
| 向量 | 0.7656 | 0.6875 | 0.7066 |
| 关键词 | 0.7969 | 0.7812 | 0.7840 |
| 原有混合 `blend` | 0.8281 | 0.7969 | 0.8012 |
| 双路融合 `rrf` | 0.8281 | 0.7969 | 0.8037 |

本组数据中，RRF 的总体召回率和 MRR 与原有混合检索相同，nDCG 小幅提高。语义改写组的 Recall@3 为 0.3125。这套小语料不能预测产品线上准确率，复测时应换入实际问题、人工标注和部署使用的向量模型。[逐组质量结果和复现命令](retrieval-quality.md)

## 首字延迟

从客户端提交 `POST /v1/agents/{id}/runs` 前到 SDK 收到首个非空 `answer.delta`。范围包括 HTTP 提交与鉴权、队列等待、工作流执行、事件持久化与 SSE 读取。每组预热 2 次，随后顺序运行 20 次。P50、P95 使用最近秩，不含预热。可使用[测量脚本](../examples/measure_ttft.py)在产品服务器复测。

固定回复组运行开始和回复两个节点。两组检索直答分别使用向量检索和 RRF，通过本机兼容模型接口取得固定三维向量，在真实 pgvector 库检索两篇合成文档，根据阈值直接输出命中段落。三组均避开付费模型调用，生成式回答的供应商排队和推理延迟需要单独实测。

| 工作流 | 成功且有文本 | 提交 P50 / P95 | 首字 P50 / P95 | 完成 P50 / P95 |
| --- | ---: | ---: | ---: | ---: |
| 固定回复 | 20/20 | 83 / 132 ms | 384 / 495 ms | 493 / 608 ms |
| 向量检索直答 | 20/20 | 89 / 117 ms | 272 / 606 ms | 398 / 694 ms |
| RRF 检索直答 | 20/20 | 103 / 186 ms | 453 / 576 ms | 604 / 834 ms |

固定回复和检索直答走不同的执行引擎（图工作流、普通问答管道）。三组分开采样，本机同期也有开发检查。这里的分位数描述单请求、热服务时的客户端体验，不宜用来推算算法本身增加了多少耗时。[60 条原始样本](../benchmarks/latency/windows-native.json)
